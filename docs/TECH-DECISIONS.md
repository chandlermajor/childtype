# 技术决策记录 / Architecture Decision Records (ADR)

本文档记录 ChildType 项目中的关键技术决策，采用 ADR（Architecture Decision Record）格式。

## ADR-001: 使用 Manifest V3

| 项目 | 内容 |
|------|------|
| **日期** | 2026-08-19 |
| **状态** | 已采纳 |
| **决策者** | 项目团队 |

**背景：** Chrome 已完全淘汰 Manifest V2，V3 是唯一支持的扩展格式。

**决策：** 使用 Chrome Extension Manifest V3。

**理由：**
1. V2 已于 2023 年被 Chrome 官方废弃，V3 是唯一合规格式
2. V3 使用 Service Worker 替代 Background Page，内存占用更小
3. V3 的 Content Security Policy 更严格，安全性更好
4. V3 的 `declarativeNetRequest` API 替代了已废弃的 `webRequest` API

**替代方案：** Manifest V2（已不可用）

**风险：** V3 的 Service Worker 可能被 Chrome 休眠，需要通过消息机制确保状态持久化。已在架构中通过 `StorageManager` 解决。

## ADR-002: 使用原生 JavaScript（无框架）

| 项目 | 内容 |
|------|------|
| **日期** | 2026-08-19 |
| **状态** | 已采纳 |
| **决策者** | 项目团队 |

**背景：** Chrome 扩展对打包体积敏感，且用户群体为儿童，需要快速加载。

**决策：** 使用原生 JavaScript (ES6+)，不引入 React、Vue、Angular 等框架。

**理由：**
1. 零依赖，打包体积小（目标 < 200KB）
2. 加载速度快，无框架启动开销
3. Chrome 扩展的 Service Worker 和 Content Script 有特殊的执行环境限制
4. 项目复杂度适中（8 个核心模块），原生 JS 可维护性足够
5. 便于理解和调试，降低维护成本

**替代方案：** React/Vue + Webpack 打包

**权衡：**
- ✅ 优势：体积小、加载快、无构建步骤
- ❌ 劣势：无虚拟 DOM，DOM 操作需手动管理
- 缓解措施：通过模块化设计（`modules/`）将 DOM 操作封装在 `KeyboardView` 中

## ADR-003: 使用 chrome.storage.local 进行数据持久化

| 项目 | 内容 |
|------|------|
| **日期** | 2026-09-11 |
| **状态** | 已采纳（替换原 ADR-003 的 sync 方案） |
| **决策者** | 项目团队 |

**背景：** 需要持久化用户设置、练习进度和成就数据。原方案使用 `chrome.storage.sync`，但在字母练习模式中，`recordKey` 每次按键都会写入进度，导致每分钟写入次数远超 `sync` 的 ~100 次/分钟配额，抛出 `MAX_WRITE_OPERATIONS_PER_MINUTE` 错误。

**决策：** 使用 `chrome.storage.local` API 作为唯一数据持久化方案。

**理由：**
1. `chrome.storage.local` 无每分钟写入频率限制（仅总容量限制 5MB，本项目数据量 < 100KB）
2. API 与 `sync` 完全一致，迁移成本极低
3. 数据仍由 Chrome 安全存储，离线可用
4. 用户数据不需要跨设备同步（儿童打字练习通常单设备使用）
5. 避免了高频写入导致的配额错误和数据丢失

**替代方案：**
- `chrome.storage.sync` — 有写入频率限制，高频写入会失败
- IndexedDB — 过于复杂，超出本项目需求
- 外部服务器 — 违反隐私优先原则，且增加复杂度

**迁移说明：**
- 所有 `chrome.storage.sync.get/set/remove/clear` 替换为 `chrome.storage.local`
- `StorageManager` 类内部实现已更新，对外接口保持不变
- 数据结构无变化，仅存储后端不同

## ADR-004: 使用 CSS Custom Properties 实现主题系统

| 项目 | 内容 |
|------|------|
| **日期** | 2026-08-19 |
| **状态** | 已采纳 |
| **决策者** | 项目团队 |

**背景：** 需要提供亮色、暗色和护眼主题切换，适配不同使用场景（白天/夜间/长时间练习）。

**决策：** 使用 CSS Custom Properties (CSS Variables) 实现主题切换。

**理由：**
1. 运行时切换无需重新加载页面
2. 变量集中管理，修改一处全局生效
3. 支持 `data-theme` 属性选择器，与 JS 设置联动简单
4. 浏览器原生支持，无额外依赖
5. 可叠加在现有 CSS 上，改造成本低

**替代方案：**
- CSS-in-JS（如 styled-components）— 需要框架支持，本项目不用
- 预编译 CSS 文件切换 — 需要重新加载页面，体验差

**实现：**
```css
:root[data-theme="light"] { --bg-primary: #FFFFFF; ... }
:root[data-theme="dark"] { --bg-primary: #1E1E2E; ... }
:root[data-theme="eye"] { --bg-primary: #E8F5E9; ... }
```

## ADR-005: 使用 Web Audio API 合成音效

| 项目 | 内容 |
|------|------|
| **日期** | 2026-08-19 |
| **状态** | 已采纳 |
| **决策者** | 项目团队 |

**背景：** 需要为正确/错误按键提供听觉反馈，增强儿童练习的趣味性。

**决策：** 使用 Web Audio API 实时合成音效，不依赖外部音频文件。

**理由：**
1. 零外部依赖，无需加载 mp3/wav 文件
2. 可程序化生成不同音高和时长的音效
3. 正确按键：短促高频「嗒」声（800Hz, 50ms）
4. 错误按键：低沉「嗡」声（200Hz, 150ms）
5. 性能开销极小，不影响打字流畅度

**替代方案：**
- 预录制音频文件 — 增加打包体积，加载慢
- 无音效 — 降低练习趣味性

## ADR-006: Content Script 模式而非 chrome_url_overrides

| 项目 | 内容 |
|------|------|
| **日期** | 2026-08-19 |
| **状态** | 已采纳 |
| **决策者** | 项目团队 |

**背景：** 需要决定打字练习界面的呈现方式。

**决策：** 使用 Content Script + DOM Overlay 方式，覆盖到当前网页上。

**理由：**
1. 用户可在任意网页上练习，不限于扩展专属页面
2. 半透明覆盖层不阻挡用户查看原网页内容
3. 符合「辅助工具」的定位，而非独立应用
4. 可通过快捷键快速切换，体验流畅

**替代方案：**
- `chrome_url_overrides` (newtab) — 只能在新标签页练习，无法在现有网页上使用
- 独立页面 — 需要用户手动导航，体验差

## ADR-007: 模块化设计（Single Responsibility Modules）

| 项目 | 内容 |
|------|------|
| **日期** | 2026-08-19 |
| **状态** | 已采纳 |
| **决策者** | 项目团队 |

**背景：** 项目包含 8 个核心业务模块，需要清晰的职责划分。

**决策：** 每个模块一个文件，遵循单一职责原则，通过 `StorageManager` 和消息机制进行通信。

**理由：**
1. 职责清晰，易于测试和维护
2. 模块间松耦合，通过消息和存储接口通信
3. 新增模块不影响现有模块
4. 方便开发者定位问题（知道功能在哪个模块）

**模块清单：**

| 模块 | 职责 | 运行环境 |
|------|------|----------|
| `KeyboardView` | 虚拟键盘渲染与交互 | Content Script |
| `TypingEngine` | 打字判定、计时、WPM 计算、阶段进阶 | Content Script |
| `StatsTracker` | 统计指标收集与展示 | Content Script |
| `StorageManager` | chrome.storage.local 封装 | Service Worker |
| `SettingsManager` | 用户偏好管理（布局、字体、主题、音效） | Service Worker |
| `AchievementSystem` | 成就定义与解锁判定 | Service Worker |
| `LevelSystem` | 等级系统与经验计算 | Service Worker |
| `SoundManager` | Web Audio API 音效 | Content Script |

## ADR-008: 字母练习 8 阶段进阶系统（替代单词/句子模式）

| 项目 | 内容 |
|------|------|
| **日期** | 2026-09-11 |
| **状态** | 已采纳 |
| **决策者** | 项目团队 |

**背景：** 原设计包含字母、单词、句子、自由四种模式。但单词/句子模式需要维护大量词库，且难度调节复杂。儿童打字学习的核心是建立全键盘肌肉记忆，分阶段循序渐进比跳跃式练习单词/句子更科学。

**决策：** 移除单词练习和句子练习模式，将字母练习重设为 8 个阶段的进阶系统，数字和符号跨多个阶段逐步引入。

**理由：**
1. **学习科学**：从基准键 → 全字母 → 数字 → 符号，符合肌肉记忆建立的自然规律
2. **难度平滑**：WPM 阈值 12→14→16→18→20→22→25→28，每阶段仅 +2，避免难度悬崖
3. **渐进引入**：数字分两阶段（1234 / 567890），符号分两阶段（常用 / 其余），避免第二阶段一次性要求大量符号
4. **自动化判定**：每批次必结算，达标升阶/不达标回落，无需用户手动选择难度
5. **维护简化**：无需维护单词库/句子库数据文件，代码量减少 ~30%

**实现细节：**
- Phase 0-3：纯字母（基准键 → 上排 → 下排 → 跨指）
- Phase 4：全字母 + 数字 1234（左手区数字）
- Phase 5：全字母 + 全数字 0-9
- Phase 6：字母数字 + 常用符号 `-=[]\;:'`
- Phase 7：全键盘（含 `.,/\``）

**风险：** 部分进阶用户可能觉得缺少单词/句子练习。缓解：自由打字模式可在任意网页练习实际文本。

## ADR-009: 移除手动难度选择（难度自动化）

| 项目 | 内容 |
|------|------|
| **日期** | 2026-09-11 |
| **状态** | 已采纳 |
| **决策者** | 项目团队 |

**背景：** 原设计在 UI 中提供简单/普通/困难三档难度供用户选择。但难度选择增加了认知负担，且与 8 阶段进阶系统语义重叠（阶段本身就代表难度）。

**决策：** 移除用户可见的难度选择器，难度完全由阶段系统内部自动调节。

**理由：**
1. **认知负担低**：儿童只需关注「当前阶段」，无需理解难度档位
2. **语义统一**：阶段 = 难度，Phase 0 相当于 Easy，Phase 7 相当于 Hard
3. **UI 简化**：Overlay 顶部移除难度按钮组，Popup 设置移除难度下拉框
4. **内部仍保留难度系数**：LevelSystem 内部仍有 `getDifficultyModifier()` 供经验计算使用，但由阶段自动映射
